AWS System Architecture

How an Indian stock price-forecasting platform is built on AWS — which service does what, why each one was chosen, how data flows from the stock exchange to the screen, and what it costs.

Version 3.0 · Date 29 October 2026 · Region ap-south-1 (Mumbai) · Status Proposed — for approval · Data provider Upstox
How to read this document

No AWS knowledge is assumed. Every service is explained in plain words before it is used, with a short note on why that service and not another. If you only have five minutes, read Section 1 and Section 9.

What this system does and does not do

It does: collect stock market data, learn patterns from history, and show forecasts on a private dashboard — an estimated closing price, an expected high and low, and a probability of gain.

It does not: place orders, touch money, or give investment advice. There is no broker connection for trading. This is a research and forecasting tool.

1The system at a glance

Five stages, left to right. Data comes in, gets cleaned, a model makes a forecast, the forecast is checked for risk, and a person sees it on a web page.

In plain words

Think of it as a factory with five rooms. The first room receives raw material (stock prices, news, oil and currency numbers). The second is a warehouse where every delivery is kept, labelled with its date. The third is a workshop that cleans the material and turns it into measurements a machine can read. The fourth is where four specialists each answer one question about the future. The fifth is the shop window where a person sees the result.

2Every AWS service, explained

AWS sells about 240 services. This system uses 18. Each card says what the service is, what it does here, and why it was picked over the alternative.

2.1 Getting data in

Amazon EventBridge SchedulerScheduling

An alarm clock for the cloud.

Starts every scheduled job at the right Indian time — fetch candles at 16:00, run the forecast at 08:30, retrain on Sunday night.

Why this: it understands time zones natively, so schedules are written as "08:30 Asia/Kolkata" instead of doing UTC arithmetic by hand and getting it wrong twice a year.

AWS LambdaCompute

Runs a small piece of code on demand, then disappears.

Fetches historical candles, downloads news, serves dashboard API requests. Roughly 12 separate functions.

Why this: you pay per millisecond of execution. These jobs run for seconds a day, so a permanently running server would be idle 99.9% of the time.

Amazon ECS FargateCompute

Runs a container for as long as you need, without managing a server.

Holds the live WebSocket connection to Upstox for the whole trading session, decodes the binary Protobuf messages, and also runs model training.

Why not Lambda: Lambda stops after 15 minutes. The market is open for 6 hours 15 minutes. Lambda physically cannot hold this connection — this is a hard limit, not a preference.

Amazon S3Storage

Unlimited file storage. Cheap, durable, never full.

The data lake. Every raw download, every cleaned dataset, every trained model and every evaluation report, each stamped with its date.

Why this: about ₹2 per GB per month, and it keeps 11 nines of durability. It is the memory of the system — if everything else is deleted, S3 can rebuild it.

2.2 Preparing the data

AWS GlueETL

A managed data-cleaning engine (Apache Spark underneath).

Adjusts prices for stock splits and bonuses, computes all technical indicators, joins news and macro features onto the right dates, and runs the data-quality checks.

Why this: rolling calculations over five years of data for 50 stocks is genuinely a Spark-sized job. Glue gives Spark without a cluster to run.

Amazon AthenaQuery

Run SQL directly on files in S3. No database to load first.

Investigating data problems, checking for gaps, and ad-hoc research questions like "show me every day RELIANCE moved more than 5%".

Why this: pay per query (about ₹400 per terabyte scanned). The alternative, a data warehouse, charges by the hour whether you query it or not.

2.3 Making the forecast

SageMaker Training JobML

A managed machine that starts, runs a training script, saves the result and shuts down.

Trains the four XGBoost models every Sunday at 02:00. About 5 minutes, roughly $0.50 a run.

Why this and not a plain container: it gives model versioning, lineage and a registry without extra code — and you pay only for the minutes it runs. Section 4.3 covers the choice in full.

SageMaker Batch TransformML

Loads saved models, scores a batch of rows, writes the answers, shuts down.

Runs the daily forecast at 08:30 — 50 rows in, 200 numbers out, about 3 minutes.

Why not a real-time endpoint: an endpoint bills 24 hours a day for a job that runs once. Batch Transform bills only the 3 minutes — about $3/month for both jobs together, against ~$145 for an idle endpoint.

Risk & Opportunity EngineOur code

Not an AWS service — plain Python running in Lambda.

Checks the four forecasts agree with each other, measures how uncertain they are, and can return No Trade when the answer is not trustworthy.

Why separate: keeping it out of the models means risk rules can change without retraining anything.

2.4 Storing and showing results

Amazon Aurora PostgreSQLDatabase

A managed PostgreSQL database that AWS keeps running and backed up.

Stores every forecast, what actually happened afterwards, model versions, user accounts and saved watchlists.

Why a real database: the dashboard asks relational questions — "accuracy for banking stocks last quarter, by model version". That is SQL's job. Use Serverless v2 so it scales down when nobody is looking.

Amazon API GatewayAPI

The front door for the dashboard's requests.

Publishes about 6 REST routes, checks the login token on each one, and limits how fast anyone can call them.

Why this: authentication, rate limiting and request validation come built in. Writing those by hand is a week of work and a security risk.

Amazon CognitoIdentity

Manages who can log in.

Email and password plus an authenticator app code. Only invited users exist — there is no public sign-up.

Why this: storing passwords safely is easy to get wrong. Cognito handles hashing, resets, sessions and MFA as a managed service.

Amazon CloudFront + S3Hosting

A global delivery network in front of static files.

Serves the React dashboard with HTTPS from a location near the user.

Why this: the dashboard is a folder of files. Putting it on a web server would mean patching that server forever.

2.5 Security and keeping it running

AWS Secrets ManagerSecurity

An encrypted vault for passwords and API keys.

Holds the Upstox Analytics Token, the news provider key and the LLM key. Code reads them at runtime; they never appear in source control.

Why this: it records who read which secret and when, and can alert before the Upstox token's one-year expiry.

AWS IAMSecurity

Decides which part of the system may do what.

Each Lambda gets its own role with the narrowest possible permission — the news fetcher cannot read the forecast database.

Why it matters: if one component is ever compromised, the damage stops at that component's permissions.

Amazon CloudWatchMonitoring

Collects logs, measurements and alarms.

Alerts when the live feed goes quiet, a day's candles are missing, forecast accuracy drops, or spend exceeds budget.

Why it matters: a data pipeline that fails silently produces wrong forecasts that look perfectly normal. Alarms are how you find out on day one, not day thirty.

AWS CDKDeployment

Describes the whole cloud setup as code.

Every service above is defined in TypeScript, in Git. Deploying is one command.

Why it matters: the system can be rebuilt from scratch in a fresh AWS account in under an hour, and every change is reviewable.

Services deliberately NOT used

Leaving things out is also a design decision. No NAT Gateway (~$35/mo) — the Upstox Analytics Token needs no static IP for market data, so no private networking is required. No ElastiCache — Aurora answers in milliseconds for a handful of users. No SageMaker real-time endpoints — forecasting runs once a day, so a 24/7 endpoint would be idle 99.8% of the time. SageMaker Training and Batch Transform are used; only the always-on endpoint is avoided. No Kinesis — the live feed goes straight from Fargate to the dashboard; there is no need to store every tick. Together these omissions save roughly $200/month.

3A day in the life of the system

What actually happens, hour by hour, on a normal trading day.

  1. 07:30 — Wake up and check the instrument list Downloads the daily Upstox instrument file so every stock's identifier is current. Identifiers change; hard-coding them silently fetches the wrong stock's data. EventBridge → Lambda → S3
  2. 08:00 — Collect news and macro data Pulls overnight business headlines and the latest oil, gold and USD/INR values. An LLM converts each article into structured numbers: sentiment, event type, companies affected. The original publication time is kept so the model can never see news from the future. Lambda → SQS → Lambda + LLM → S3
  3. 08:10 — Build the features Glue adjusts for any corporate action, computes the technical indicators, joins yesterday's news and macro features, and runs 14 data-quality checks. If a check fails, the pipeline stops here rather than forecasting on bad data. AWS Glue → S3
  4. 08:30 — Make the forecast The four models each answer their question for every stock. The Risk Engine checks the answers are coherent — low must be below high, close must sit between them — and assigns a risk score or returns No Trade. Fargate → Lambda → Aurora
  5. 09:15 — Market opens, live prices start A Fargate container connects to the Upstox WebSocket and decodes the binary feed. Prices stream to the dashboard. Individual ticks are not written to the database — that would be millions of pointless writes per day. ECS Fargate → WebSocket → Dashboard
  6. 15:30 — Market closes The streaming container shuts itself down. Nothing runs, nothing is billed. EventBridge stops the task
  7. 16:00 — Record what actually happened Downloads the day's official candles and compares them against forecasts whose horizon has now matured. This is the scoreboard: was the estimate right? Lambda → S3 → Aurora
  8. Sunday 02:00 — Retrain All four models retrain on data including the past week, are tested against simple baselines, and are only promoted if they beat them. If they do not, last week's models stay. Fargate → S3 → model registry

4The decisions worth explaining

4.1 Why Upstox and not Zerodha

Both are reputable Indian brokers with developer APIs. For this system — which only reads data and never places an order — Upstox is clearly better. The detail is in Document 3; the summary:

Upstox Analytics Token Chosen
  • Free — ₹0 per month, confirmed in the official documentation
  • Valid one year — generated once, not daily
  • No static IP needed for market data, history or WebSocket
  • Daily candles back to January 2000; 10 years per request
  • Read-only by design — it cannot place an order even by mistake
Zerodha Kite Connect Not chosen
  • ₹500/month — market data is not in the free tier
  • Token expires daily and renewal needs an interactive login with 2FA — it cannot be fully automated
  • Static IP required for orders, forcing a NAT Gateway (~$35/mo)
  • Trading-capable credentials in a system that should never trade
The decisive point

The Zerodha token must be regenerated every morning through a browser login with two-factor authentication. That is a person doing a manual step before 08:30, every single working day, forever. The Upstox token lasts a year. For a system that runs unattended, this difference matters more than the ₹500.

4.2 Why a database as well as S3

They do different jobs and the distinction is worth being clear about.

QuestionAmazon S3Aurora PostgreSQL

Putting forecasts only in S3 would mean scanning files to answer a dashboard query. Putting training data in Aurora would cost many times more and be slower for bulk reads.

4.3 How SageMaker is used — and how it is not

SageMaker is AWS's managed machine-learning platform. This system uses two parts of it and deliberately avoids a third.

PartUsed?What it does hereCost
Training JobYesFits the four models weekly, then shuts down~$1/mo
Batch TransformYesScores 50 rows daily in ~3 min, then shuts down~$2/mo
Real-time endpointNoA server held ready 24/7 for instant answers~$145/mo

The distinction matters. A real-time endpoint is what most SageMaker tutorials show, and it is the wrong shape for this system: the forecast runs once a day, so an always-on endpoint would sit idle 99.8% of the time and still bill for it. Batch Transform does the identical scoring work, bills only the three minutes it runs, and costs about a thirteenth as much.

Why SageMaker rather than a plain container: the training itself is small enough to run anywhere — XGBoost on 50 stocks × 5 years fits in minutes on an ordinary CPU, with no GPU needed. What SageMaker adds is the surrounding discipline: every training run is versioned, every model file is traceable to the exact data and code that produced it, and promotion from "trained" to "live" is an explicit, recorded step. For a forecasting system that must be auditable, that bookkeeping is the point — and it arrives without writing any of it ourselves.

What would change the answer: if inference were ever needed on demand rather than once a morning, the real-time endpoint becomes correct despite the cost. Nothing in the current design points that way.

4.4 Why four separate models

Each question has a different shape, so each gets its own model. Section 2 of Document 2 covers this in full, but briefly: the highest price over five days is a maximum of five numbers, which behaves differently from an average; and a probability must be calibrated, which is a different training objective entirely. One model forced to answer all four questions answers all of them worse.

The two data problems that break forecasting systems

1. Corporate actions. When a stock splits 1-for-5, the price drops 80% overnight. To a naive pipeline that looks like an 80% crash and poisons every calculation that touches that date — for a 200-day average, that is 200 subsequent days. Prices must be split-adjusted, and any single-day move above 25% is automatically flagged for review.

2. Point-in-time correctness. A model must only ever see what was genuinely knowable on that date. News carries its publication timestamp, not its ingestion timestamp. This sounds obvious and is violated constantly — it is the main reason backtests look brilliant and live performance does not.

Exchange data carries redistribution restrictions. Having free API access is not the same as having the right to display that data publicly or to store it indefinitely for model training.

Keeping the dashboard private and invite-only avoids the question for a research MVP. Before showing this to anyone outside the company, written clarification is needed from Upstox and/or the exchange on three points: storage (how long may data be retained), training (may it be used to train models), and display (who may see it).

Why baselines come before models (stage 3)

A baseline is a deliberately stupid prediction — "tomorrow's price equals today's". If a sophisticated model cannot beat it, the model is worthless no matter how impressive its accuracy number looks. Building baselines first means there is always something honest to compare against, and it is the single cheapest protection against fooling yourself.

Where the savings came from

An earlier draft of this architecture came to roughly $375/month. Four changes removed about $200 of that with no loss of capability: batch forecasting instead of a 24/7 SageMaker endpoint (−$144), no ElastiCache (−$25), weekly instead of daily retraining (−$25), and choosing Upstox, which removes both the ₹500 fee and the NAT Gateway (−$41).

Biggest cost, and how to cut it

Aurora at ~$45 is the largest single line. If the budget needs to be tighter, forecasts could be served from DynamoDB or even S3 and the database dropped entirely — saving about $45 at the cost of flexible SQL reporting. That is a reasonable trade for a pure MVP, and a poor one once model-performance analysis becomes a regular activity. The recommendation is to keep Aurora.

The one thing to be clear about with any audience

Realistic accuracy for next-day direction on liquid large-cap equities is roughly 52–56%. Published claims of 95%+ accuracy almost always come from measuring the wrong thing — usually predicting the price level rather than the change, which scores beautifully while predicting nothing useful.

If this system ever reports above 60% on unseen data, the correct response is to look for a bug, not to celebrate. That rule is built into the model promotion gate.
