How the four predictive models work

ModelExact target (example 5 trading sessions)Algorithm & evaluation
Future closeReturn from price at forecast cutoff to close on session t+5; convert to predicted priceXGBoost regression; compare to naive no-change baseline, MAE / RMSE
Future highMaximum high across sessions t+1…t+5XGBoost regression; error, coverage and consistency checks
Future lowMinimum low across sessions t+1…t+5XGBoost regression; error, coverage and consistency checks
Gain probabilityProbability(close at t+5 > reference at forecast cutoff), net of no costs unless explicitly modeledXGBoost classifier with held-out probability calibration; Brier score / reliability curve

Features available at prediction time

Lagged returns, moving averages, RSI/MACD, ATR, realized volatility, relative volume, market/index returns, sector moves, macro indicators and last-published news sentiment — all matched using available_at ≤ forecast cutoff. Include adjusted-price continuity, missingness flags and source freshness.

LLM role — structured understanding, not stock-price oracle

Use LLM to classify permitted news metadata into impacted instruments, event category, sentiment/polarity, relevance, publication time, and extraction confidence. Validate against instrument master; deduplicate events; quarantine low-confidence matches; save model version and structured output.

A deterministic aggregation job rolls eligible events into features such as news_sentiment_24h, negative_event_count_3d and days_since_earnings_news. The XGBoost models consume those numeric features; LLM text alone does not directly approve a trade.

Risk & opportunity engine

Separate policy layer checks predicted upside/downside, trading liquidity, bad or stale news, inconsistent predicted ranges, out-of-distribution features and low confidence. It can return Watch, Candidate or No-Trade with reason codes; these are research outputs, not broker orders.

CRITICAL VALIDATION RULES

Prevent misleading forecasts

  • Use walk-forward chronological splits, with purging/embargo where target windows overlap; do not random-split time series.
  • Avoid look-ahead: macro revisions, headlines published later, and adjusted bars must not silently leak the future.
  • Use an as-of market cutoff and a consistent reference price for all four targets.
  • Compare against naive baseline and assess market-regime robustness.
  • Calibrate claimed probability of gain and assess confidence after costs if discussing trade economics.
  • Monitor drift, label delays, liquidity, corporate actions and delisted symbols.
  • Use one shared training framework with four output targets initially; four separate deployed services are unnecessary.
Suggested cadence: ingest daily, infer once per valid market session after inputs are finalized, and retrain weekly or only when monitoring justifies it. These are starting defaults, not guaranteed optimal schedules.
Where Athena fits: Glue Data Catalog describes S3-backed Parquet tables. Athena queries the S3 data with SQL for exploration, validation, lineage audits and cohort analysis. It does not host models or serve live dashboard requests.

Example SQL — inspect daily OHLCV coverage

SELECT session_date,
       COUNT(DISTINCT instrument_key) AS symbols,
       COUNT(*) AS bars,
       SUM(CASE WHEN close <= 0 OR high < low THEN 1 ELSE 0 END) AS bad_bars
FROM stocklake_silver.adjusted_ohlcv
WHERE session_date BETWEEN DATE '2026-10-01' AND DATE '2026-10-29'
GROUP BY session_date
ORDER BY session_date;

Example SQL — investigate news publication-time safety

SELECT f.asof_date, f.instrument_key,
       COUNT(n.event_id) AS known_news_count
FROM stocklake_gold.daily_features f
LEFT JOIN stocklake_silver.news_events n
  ON f.instrument_key = n.instrument_key
 AND n.published_at <= f.cutoff_utc
 AND n.analyzed_at <= f.cutoff_utc
 AND n.published_at > f.cutoff_utc - INTERVAL '3' DAY
GROUP BY f.asof_date, f.instrument_key
ORDER BY f.asof_date DESC
LIMIT 100;

Milestone 1 · Market-data foundation

Finalize available historical Upstox data/licensing, instrument master, exchange calendar, corporate-action handling and point-in-time timestamp rules. Set S3 paths, versioning, encryption and retention. Success: a reproducible sample of adjusted daily OHLCV covering the target universe.

Milestone 2 · Raw data ingestion

EventBridge starts Step Functions (or a simple Lambda coordinator). Separate collectors fetch historical candles, permitted news and macro vintages; save each batch to dated raw S3 partitions with idempotency keys, ingestion timestamps and failure alerts. Success: rerun/backfill without duplicate records.

Milestone 3 · News extraction & structured features

Implement prompt/schema validation, deterministic ticker matching, event deduplication, review thresholds, provider usage controls and a small human-labeled evaluation set. Store structured events in silver S3; generate rolling aggregates. Success: measurable ticker-precision and sentiment-quality checks.

Milestone 4 · Glue & Athena

Transform raw files to adjusted and validated Parquet, register bronze/silver/gold tables in Glue Data Catalog, set up Athena workgroup and S3 query-result output, write SQL coverage/duplicate/leakage checks. Success: daily feature snapshots queryable by symbol and cutoff.

Milestone 5 · Baselines then XGBoost

Define each five-session target; train naive/simple baselines; build four XGBoost targets with chronological walk-forward evaluation and tuned but bounded search. Pin training dataset, feature schema and model artifacts. Success: independently tested metrics that improve on baselines without leakage.

Milestone 6 · Prediction + recommendation engine

Scheduled ECS inference loads approved models and gold features; applies deterministic consistency/risk policies; writes versioned forecasts, decisions and explanations to Aurora. Lambda serves them through existing API Gateway. Success: dashboard shows as-of time, forecast horizon, model version and No-Trade reason.

Milestone 7 · Outcomes, monitoring & rollout

At target maturity, save realized close/high/low and calculate forecast errors. Monitor drift, calibration, missing data, runtime/cost and performance by market regime; use champion/challenger promotion. Success: credible paper-testing before any consequential trading use.

Compute choice: Your existing ECS/Fargate skills make scheduled Python/XGBoost batch tasks a sensible MVP; use AWS Glue only where its managed ETL benefit justifies cost/scale, and consider SageMaker later for large experiments or managed ML workflows. No always-running ML service is required for daily batch predictions.
